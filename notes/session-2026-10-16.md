## Data format

The Blender exporter (`scan_selected_objects` in `blender/test_scripts/run_fracture.py`) now writes:

```json
{"fps": 24.0, "frames": {"1": {"Cube_cell": [px, py, pz, qx, qy, qz], ...}, "2": {...}}}
```

- Frames come first, then objects. Previously it was objects, then frames.
- `fps` is the scene's `render.fps / render.fps_base`, so Roblox can time keyframes in seconds.
- Positions are multiplied by 10000 and quaternions by 100000, then rounded. The quaternion's w is dropped and rebuilt in Roblox.
- It exports every mesh in the scene that has baked animation, no matter what's selected. The function name still says "selected".
- A frame only lists the objects keyed on it. A piece that has stopped moving can be missing from later frames.

## Roblox: `KeyframeData.luau`

- **`Decode`** reads the format above. Each part's rest pose is its first keyed frame, and it records `firstFrame` so the clip starts at 0 seconds. It now errors clearly if the JSON isn't `{fps, frames}` or a keyframe isn't 6 numbers.
- **`GetConstraints(assembly: Model)`** maps part names to the AnimationConstraint driving them, through `Attachment1.Parent`. It errors if the model's `PrimaryPart` isn't `KF_ROOT`.
- **`ApplyFrame`** sets each joint's `Transform` to `rest:Inverse() * pose`.
- **`ApplyAnimationDataToAssembly`** builds a `KeyframeSequence` in `workspace`, named after the model:
  - `Keyframe.Time = (frame - firstFrame) / fps`
  - Each keyframe holds a `KF_ROOT` pose with one pose per part inside it, using the same rest-relative CFrame as `ApplyFrame`.
  - Parts with no joint are skipped. `Loop` is off.
- **`CheckRig`** prints, for each part, how far its joint's rest frame is from that part's frame-1 data. All parts should share one offset and 0 degrees. It runs every time data is pasted.
- **`ToRobloxAxes`** is now `(x, y, z) → (-x, z, y)`. See "Pieces landing in the wrong places" below.

## Roblox: `Skeleton.luau`

`Skeleton.Generate(assembly)` now:

- Creates or reuses an anchored, invisible `KF_ROOT` at the average part position, and sets it as `PrimaryPart`.
- Unanchors every other part, so only the root is anchored.
- Gives each part a `KFAttachment` at its **pivot position**. It uses `PivotOffset.Position` only, because the pivot's 90° rotation is just the importer's Z-up axis frame.
- Gives each part an AnimationConstraint, named after the part, with `IsKinematic = true`. `Attachment0` is a new attachment on `KF_ROOT` placed at the part's attachment; `Attachment1` is the part's `KFAttachment`.
- Skips parts that already have an AnimationConstraint, so running it twice doesn't create duplicates. This also means **old rigs aren't updated**: delete `KF_ROOT` and every part's constraint and `KFAttachment`, then run it again.
- Adds an `AnimationController` with an `Animator`, or reuses an existing Humanoid or AnimationController. The Animation Editor needs one to recognise the rig.

## Pieces landing in the wrong places

Two separate bugs, found one after the other:

1. **Joints ignored the pivot (fixed and confirmed).** The Roblox importer puts each MeshPart's pivot at the Blender object's origin. The part's `Position` is the mesh's centre. The data moves the Blender origin, but the joints were placed at the centre, so each piece rotated around the wrong point. With the pivot fix, `Cube_cell.008` ended within 0.01° and at the same height (0.337) as Blender's frame 250.
2. **Horizontal axes were mirrored (fixed, not yet checked in Studio).** With all ten cells, `CheckRig` showed a different X/Z offset for every part. With `(x, y, z) → (-x, z, y)` instead of `(x, z, -y)`, all ten share exactly one offset, (27.624, 0, -8.308). So the importer flips Blender's X and Y compared with the old mapping. Height was already right, which is why the single-part test passed.

Ruled out along the way:

- **Scale:** sizes match 1:1. `Cube_cell.008` is 1.3 × 1.66 × 1.34 m in Blender and 1.302 × 1.336 × 1.662 studs in Roblox.
- **Import pose:** the meshes were exported on frame 1.
- **The bake:** it calls Blender's own `rigidbody.bake_to_keyframes`.
- **Losing frames after 154:** at the end of the clip, the joint `Transform` matched Blender's frame 250. That theory came from a screenshot taken before the clip had finished.
